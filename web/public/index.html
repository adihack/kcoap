kcoap

kcoap: CoAP, OSCORE and EDHOC for Kotlin Multiplatform

One implementation in common Kotlin for Android, iOS, macOS, JVM servers, Linux gateways, browsers and Node.js. Checked against the RFCs’ own test vectors, and in live interop with libcoap and libedhoc.

In development Version 0.1.0-SNAPSHOT. Nothing is released yet: you build it from source today.

Server.kt

// A CoAP server on UDP port 5683
var stored = "nothing yet"
val server = CoapServer(KtorUdpTransport.bind(port = 5683), scope) {
    resource("hello") {
        get { CoapResponse.content("Hello, $peer") }
    }
    resource("store") {
        get { CoapResponse.content(stored) }
        put {
            stored = payloadAsText()
            CoapResponse.changed()
        }
    }
}

Client.kt

// Every call suspends until the whole response has arrived:
// separate responses and Block-wise transfers are handled for you.
val client = CoapClient(KtorUdpTransport.bind(), scope)
val server = "coap://127.0.0.1:5683"

println(client.get("$server/hello").payloadAsText())

val body = "on".encodeToByteArray()
client.put("$server/store", body, ContentFormat.TEXT_PLAIN)
println(client.get("$server/store").payloadAsText())  // on

val links = client.discover(server)  // GET /.well-known/core

Observe.kt

// Server: an observable resource, notified every second
val clock = object : ObservableResource("time") {
    override suspend fun handleGet(context: RequestContext) =
        CoapResponse.content(Clock.System.now().toString())
}
val transport = KtorUdpTransport.bind(port = 5683)
val server = CoapServer(transport, scope) { add(clock) }
scope.launch {
    while (isActive) {
        delay(1.seconds)
        clock.notifyObservers()
    }
}

// Client: a cold Flow, registered while it is collected
client.observe("coap://127.0.0.1:5683/time").take(3).collect {
    println("time: ${it.payloadAsText()}")
}

Secure.kt

// EDHOC, then OSCORE (RFC 9668): the first OSCORE request
// carries EDHOC message_3, so it takes two round trips in all.
// initiatorConfig holds your credential and the ones you trust.
val security = PeerSecurity()
val client = CoapClient(
    KtorUdpTransport.bind(),
    scope,
    CoapClientConfig { this.security = security },
)
val server = CoapUri.parse("coap://192.0.2.1")
val (session, protection) =
    EdhocClientHandshake.over(client, server, initiatorConfig, crypto)
        .runCombined()
security.install(client, server, protection)

client.get("coap://192.0.2.1/lights")  // protected and verified

Requests are suspend functions, Observe is a Flow, and scope is your CoroutineScope. More in the client and server guide.

Highlights

Built to be checked

Each highlight is backed by tests in the repository. The features page has the detail and names the evidence.

RFC vectors, byte for byte

Every OSCORE vector of RFC 8613 Appendix C. Both EDHOC traces of RFC 9529, in both roles, and its invalid messages. RFC 9668 Figure 4 and the RFC 8323 framing figures.

Live interop in both roles

CI runs kcoap as client and as server against libcoap 4.3.5b, and as Initiator and as Responder against libedhoc. Deviations found in the peers are listed, pinned by tests where they can be, and never copied.

Post-quantum EDHOC

The KEM-based key exchange of draft-ietf-lake-pqsuites as suite −24: ML-KEM-512 and ML-DSA-44, checked against a subset of NIST’s ACVP vectors and live against libedhoc’s liboqs build. Runs on the JVM; an Android app builds with it, but has not run it on a device.

Q-Block, RFC 9177

Large bodies in bursts that recover lost blocks without stopping. Client and server, with Observe and under OSCORE, over UDP, TCP and WebSockets. Off by default.

Fail-closed message security

A server with OSCORE refuses unprotected requests before any handler sees them. A client acts only on responses it verified, and never sends plaintext unless you allow it.

Sans-IO state machines

Messaging, Q-Block and EDHOC take bytes and time and return bytes and timers, so each layer is tested with fixed vectors on virtual time. EDHOC’s Initiator and Responder are public API.

One code base, every target

All protocol code is common Kotlin, with no expect/actual. The same common tests run on the JVM, Linux, macOS, the iOS simulator, and JS and Wasm on Node.js.

Capability-aware crypto

One asynchronous CryptoBackend over JCA, CryptoKit, OpenSSL or WebCrypto. EDHOC offers only the suites the backend can run. Keys are opaque handles, so a hardware backend can hold them; none ships yet.

A build that guards the API

ABI dumps for every published module, common-only protocol modules, Android API level 26 checks, and a DCO sign-off check on every pull request.

Architecture

Layers that compose

kcoap follows the layering of RFC 8613 and keeps each layer separate, so a feature works the same wherever it runs.

  • One endpoint, every transportBlock-wise, Observe, Q-Block and OSCORE run the same code over UDP, TCP and WebSockets.
  • Protection end to endOSCORE protects each request and response end to end, the same on every transport. EDHOC runs over CoAP and hands its keys to OSCORE.
  • Sockets at the edgeThe protocol cores never touch a socket. Thin adapters bind them to ktor on each runtime.

Not built yet: DTLS for coaps://, which comes last; TLS on the server side, which ends at a reverse proxy for now, and coaps+tcp beyond the JVM; outer Block-wise for proxies. Read the architecture.

Security

From handshake to protected request in two round trips

EDHOC authenticates both sides and derives the OSCORE keys. With the combined request of RFC 9668, the client’s first OSCORE request carries the last EDHOC message.

  • EDHOC, RFC 9528Methods 0–3 and cipher suites 0–6 and 24. Both RFC 9529 traces replay byte for byte, in both roles.
  • Fails closedWith OSCORE configured, a server answers an unprotected request with 4.01 before any handler runs, and a client acts only on responses it verified.
  • Post-quantum suite −24ML-KEM-512 and ML-DSA-44 on the JVM, live against libedhoc in both roles. Not run on an Android device yet.

Still open: the reverse flow (RFC 9528 Appendix A.2.2), the client’s EDHOC error after a failed message_2 or message_4, the sequential fallback for a large combined request, and an independent peer for EDHOC over CoAP. See the checklist.

Q-Block

Large bodies over lossy links

RFC 9177 sends a body in bursts of blocks instead of one round trip per block, and asks again only for the blocks that went missing.

  • Bursts, not round tripsNon-confirmable requests move a body in bursts of up to MAX_PAYLOADS blocks, 10 by default.
  • Recovery without restartingThe receiver asks for exactly the blocks it is missing, in one 4.08 for an upload, and only those travel again.
  • Off until you turn it onEnable it on both sides. A client set to probe asks each server once and falls back to RFC 7959 Block-wise.

Evidence: every figure of RFC 9177 replays as a test on virtual time; soaks run at 10 % and 30 % loss; libcoap 4.3.5b in both roles. ADR 0006.

Platforms

One code base, seven Kotlin targets

All protocol code is common Kotlin. The platforms differ only in what their cryptography offers, which the backend reports, so EDHOC offers only the cipher suites that run there.

  • Same tests everywhereThe common tests run in CI on the JVM, Linux, macOS, the iOS simulator, and JS and Wasm on Node.js.
  • Android from API level 26Android apps use the JVM artifacts. CI checks the API level and builds a sample app with R8 and lint; it has not run on a device yet.
  • Browsers over WebSocketsBrowsers have no UDP. They reach devices through a CoAP proxy such as libcoap’s, with OSCORE and EDHOC end to end. CI runs that path with a WebSocket-only kcoap client on the JVM; not yet from a browser.

Interop

Cross-tested against independent implementations

CI builds libcoap and libedhoc from pinned sources and runs kcoap against them, in both roles wherever both apply.

  • Every suite and method both sides haveEDHOC suites 0, 2, 4 and 24 with methods 0–3, as Initiator and as Responder: 32 sessions, plus the post-quantum suite.
  • Both sides derive the same keysA session passes when both sides hold the same OSCORE Master Secret and Salt, identifiers and exporter output, before and after a key update.
  • Upstream deviations pinnedWhere libcoap or libedhoc deviates from an RFC, the interop notes list it and a test pins it where it can. kcoap does not copy it.

Not cross-tested yet: EDHOC over CoAP against an independent peer, cipher suites 1, 3, 5 and 6, DTLS, and kcoap as a TLS server. Interop details.

Get started

Use it today, before the first release

Nothing is on Maven Central yet. Publish a snapshot from a clone into your local Maven repository, then depend on it like any other library.

  1. Clone and publish to Maven Local

    Needs a JDK 17 or newer; Gradle downloads the rest. For iOS and macOS apps, run it on a Mac with Xcode.

    Terminal

    git clone --branch feat/protocol-core https://github.com/adihack/kcoap.git
cd kcoap
# dev.kcoap:*:0.1.0-SNAPSHOT into ~/.m2/repository
./gradlew publishToMavenLocal

  2. Add the modules you need

    Use one version for every kcoap module. In a multiplatform project the same coordinates go into commonMain.dependencies, except the adapters a target lacks.

    Kotlin DSL

    build.gradle.kts

    // build.gradle.kts
repositories {
    // kcoap 0.1.0-SNAPSHOT, until the first release is on Maven Central
    mavenLocal()
    mavenCentral()  // kcoap's own dependencies
}

dependencies {
    val kcoap = "0.1.0-SNAPSHOT"
    implementation("dev.kcoap:kcoap-coap:$kcoap")            // client, server
    implementation("dev.kcoap:kcoap-transport-ktor:$kcoap")  // UDP, TCP
    implementation("dev.kcoap:kcoap-crypto-default:$kcoap")  // cryptography
    implementation("dev.kcoap:kcoap-oscore:$kcoap")          // OSCORE
    implementation("dev.kcoap:kcoap-edhoc-oscore:$kcoap")    // EDHOC, OSCORE
}

    Version catalog

    gradle/libs.versions.toml

    # gradle/libs.versions.toml
[versions]
kcoap = "0.1.0-SNAPSHOT"

[libraries]
kcoap-coap = { module = "dev.kcoap:kcoap-coap", version.ref = "kcoap" }
kcoap-transport-ktor = { module = "dev.kcoap:kcoap-transport-ktor", version.ref = "kcoap" }
kcoap-crypto-default = { module = "dev.kcoap:kcoap-crypto-default", version.ref = "kcoap" }
kcoap-oscore = { module = "dev.kcoap:kcoap-oscore", version.ref = "kcoap" }
kcoap-edhoc-oscore = { module = "dev.kcoap:kcoap-edhoc-oscore", version.ref = "kcoap" }

[bundles]
kcoap = [
    "kcoap-coap",
    "kcoap-transport-ktor",
    "kcoap-crypto-default",
    "kcoap-oscore",
    "kcoap-edhoc-oscore",

    build.gradle.kts

    // build.gradle.kts

    mavenLocal()
    mavenCentral()
}

    implementation(libs.bundles.kcoap)

    Each guide lists the modules for that target, what works there today and what does not.

Releases and versioning

Not there yet

  • Open: DTLS (coaps://): interfaces only; the engine comes last. OSCORE and EDHOC protect messages end to end in the meantime.
  • Open: TLS: a coaps+tcp client on the JVM only, and no TLS server of kcoap’s own; servers terminate TLS at a reverse proxy.
  • Open: OSCORE Appendix B.2: re-deriving the ID Context is deferred.
  • Open: Swift-facing API: no XCFramework, Swift package or Flow bridge yet.
  • Open: Maven Central: the dev.kcoap namespace is verified; the signing key and the publishing secrets are not set up yet.
  • Open: API reference: goes online with the first release.
