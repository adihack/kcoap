Process

How a tag becomes a release

A release is a v* tag. The version is the tag without the v; between releases the build holds the next version with -SNAPSHOT.

  1. Test

    The whole CI workflow runs again: unit tests on every target, the coverage floor, interop with libcoap and libedhoc, the Apple targets and the API reference. Nothing is published if any of it fails.

  2. Publish

    A macOS runner builds every module for every target. Releases always go to GitHub Packages, and to Maven Central once its namespace and secrets are set up; they are signed once a signing key is.

  3. Release notes

    A GitHub Release with notes generated from the merged pull requests. A version with a -, such as 0.2.0-rc1, is marked as a pre-release.

  4. API reference

    Dokka builds the reference and the workflow deploys it to GitHub Pages.

Checklist

Before 0.1.0 is tagged

The releasing guide lists what has to be true first. On 6 November 2026:

  • The release freeze has merged and CI is green on main. Pull request #1 is still a draft.
  • Nothing deprecated is left in the API: the constructors of CoapEndpointConfig and CoapClientConfig, deprecated for their builders, are removed.
  • CHANGELOG.md has an entry for the version, with migration notes.
  • The dev.kcoap namespace is verified in Maven Central’s portal, through a DNS record on kcoap.dev.
  • The Maven Central and signing secrets are set.
  • Every POM names the license, the website, the maintainer, the issue tracker and the sources.
  • Snapshots publish to Maven Local, and CI builds an Android consumer app against them.
  • The ABI dumps are current. CI checks them on every pull request; the check is repeated for the tag.
  • v* tags are protected, and GitHub Pages serves from GitHub Actions.

Versioning

The versioning policy in short

Semantic Versioning 2.0.0, one version for every module, and a build that checks the public API on every change.

One version for all modules

Every published module is released at once with the same version. Use one version for all kcoap modules in a build: they share internal plumbing, and mixed versions are not supported.

Before 1.0

A minor release, such as 0.1.0 to 0.2.0, may break the API; each break is listed in the changelog under “Changed (breaking)” with a migration note. A patch release is fixes only and never breaks the API.

From 1.0

Breaking changes only in a major release, after a deprecation that lasts at least one minor release. A security fix that cannot avoid a break, or a raised minimum, may break in a minor.

API tiers

The stable API is what the ABI dumps hold. @ExperimentalKcoapApi may change in any minor release; @InternalKcoapApi is not API. Unpublished modules promise nothing.

On the wire

A deviation from an RFC is a bug, fixed in the next patch or minor. A default that changes the wire, such as turning Q-Block on, changes only in a minor or major release. Suite −24 follows its draft.

Security fixes

Listed under “Security” in the changelog. A behaviour change that removes a vulnerability may ship in a patch release.

Raising a minimum is a breaking change, in a minor or major release only.

Where releases will be

Maven Central

After the first release, once the dev.kcoap namespace is verified: dev.kcoap:<module>:<version> from mavenCentral(), with no other repository. not yet

GitHub Packages

Every release, from https://maven.pkg.github.com/adihack/kcoap. Gradle needs a GitHub token with read:packages to read it, even for a public package. not yet

GitHub Releases

One per tag, with notes generated from the merged pull requests. The artifacts are in the Maven repositories, not attached to the release. GitHub Releases.

API reference

Published to adihack.github.io/kcoap with the first release; it is not online yet. Until then, ./gradlew dokkaGenerate builds it into build/dokka/html.
