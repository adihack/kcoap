Conformance

RFC vectors, byte for byte

Where a specification prints test vectors, kcoap replays them and compares every intermediate value, not only the result.

  • Done: OSCORE: RFC 8613 Appendix C.1 to C.8, from context derivation to protected messages, on both sides.
  • Done: EDHOC: both traces of RFC 9529, every printed value, as Initiator and as Responder, and the invalid messages of its section 4.
  • Done: The combined EDHOC and OSCORE request of RFC 9668 Figure 4, and the RFC 8323 framing of Figure 5 and Figures 11 and 12.
  • Done: Every Q-Block figure of RFC 9177, 2 to 20, as a script on virtual time over the real messaging layer.
  • Done: Cryptography: all 24 AES-CCM packets of RFC 3610, RFC 5869 HKDF, FIPS 197, SP 800-185 KMAC256 samples 1 to 4, and a subset of NIST’s ACVP vectors for ML-KEM and ML-DSA.
Evidence and open items
  • Rfc8613VectorsTest, Rfc9529TraceTest, Rfc9529InvalidTracesTest, QBlockFiguresTest, AesCcmTest, MlKemKnownAnswerTest, MlDsaKnownAnswerTest.
  • Open: one case each for RFC 7748, RFC 8032 and FIPS 202; KMAC256 samples 5 and 6; no CI check yet that the scripts reproduce the committed vectors.

Interop

Live interop in both roles

CI builds libcoap and libedhoc from pinned sources and runs kcoap against them: as client and as server, as Initiator and as Responder.

libcoap’s maintainers include RFC authors, and libedhoc is an independent EDHOC implementation in C. Against libcoap 4.3.5b, kcoap is tested over UDP, TCP and WebSockets, with Block-wise, Observe, Q-Block, Echo and OSCORE, and as a TLS client over coaps+tcp and coaps+ws. libcoap’s forward-proxy also stands between a WebSocket-only kcoap client and a kcoap device on UDP, with OSCORE, EDHOC and the combined request end to end. Against libedhoc, every cipher suite and method both implement runs in both roles, and a session passes only when both sides derive the same OSCORE Master Secret and Salt, identifiers and exporter output, before and after a key update.

Not cross-tested yet: EDHOC over CoAP and the combined request against an independent peer; cipher suites 1, 3, 5 and 6, which libedhoc lacks; DTLS; kcoap as a TLS server; the proxy path from a real browser; interop under systematic network impairment. Interop runs on the JVM target; the protocol code is the same common code everywhere.

Deviations found in the peers

Each is listed in the interop notes and pinned by an upstream… test where it can be. kcoap does not copy them.

  • Open: libcoap 4.3.5b protects only one response per request, so Q-Block under OSCORE is cross-tested kcoap against kcoap only.
  • Open: libcoap answers a request with both Block2 and Q-Block2 with 4.00 instead of 4.02, and keeps Q-Block for a whole session.
  • Open: libcoap’s WebSocket server aborts on frames above 1472 bytes, so the tests cap its message size.
  • Open: libedhoc’s Responder supports only its last configured suite, and accepts unknown critical EAD without a callback.
  • Open: libcoap’s forward-proxy reaches devices only on port 5683, drops an OSCORE request that names its target in Proxy-Uri, sends a deregistration on a new token, and corrupts request bodies of several blocks, which keeps post-quantum EDHOC off that path (ADR 0009).

On kcoap’s side

The interop notes record that no deviation from RFC 9528 or draft-ietf-lake-pqsuites-02 was found on kcoap’s side.

The peers build from source on every CI run, libcoap at tag v4.3.5b and libedhoc at commit 0363bd3, with kcoap’s own edhoc_peer around libedhoc. Q-Block soaks run against libcoap at 10 % loss on both sides.

A test runs each peer in Docker and plays one role while kcoap plays the other; for EDHOC, both sides then compare what they derived.

Post-quantum

Post-quantum EDHOC

The KEM-based key exchange of draft-ietf-lake-pqsuites, as libedhoc’s private cipher suite −24: ML-KEM-512 for the key exchange, ML-DSA-44 for signatures.

  • Done: Round trips with real ML-KEM and ML-DSA on Bouncy Castle 1.86.
  • Done: ML-KEM and ML-DSA checked against a subset of NIST’s ACVP vectors, at a pinned ACVP-Server commit.
  • Done: Live against libedhoc’s liboqs build, in both roles, with CCS and ML-DSA-44 X.509 credentials.
  • Done: Method 0 only: methods 1 to 3 need static Diffie-Hellman keys, which a KEM suite has not, so they are refused.
  • Open: On the JVM only, through kcoap-crypto-bc, which wraps the classical backend you pass. An Android app builds and shrinks with it, but has not run it on a device. Other platforms, and suite −24 through EDHOC over CoAP, are still to do.

Q-Block

Q-Block, RFC 9177

Large bodies travel in bursts of Non-confirmable blocks, and a lost block is asked for again on its own, without restarting the transfer.

  • Done: Client and server, uploads (Q-Block1) and downloads (Q-Block2), over UDP, TCP and WebSockets.
  • Done: With Observe: each change goes out as one body, with a new ETag.
  • Done: Under OSCORE, opt-in on both sides, with a replay window per request.
  • Done: Before a burst to an unverified address, the server checks it with Echo.
  • Done: Off by default. A client set to probe asks each server once and falls back to RFC 7959 Block-wise.

Evidence: every RFC 9177 figure on virtual time; soaks of 20 seeds at 10 % and 30 % loss; libcoap 4.3.5b in both roles. Open: the nightly soak is not scheduled in CI yet. ADR 0006.

QBlock.kt

// Server: Q-Block is off by default
val serverConfig = CoapServerConfig(
    qBlock = QBlockServerConfig(isEnabled = true),
)
val transport = KtorUdpTransport.bind(port = 5683)
val server = CoapServer(transport, scope, serverConfig) {
    // resources
}

// Client: OFF by default; PROBE asks each server once
val clientConfig = CoapClientConfig {
    qBlock = QBlockClientConfig(mode = QBlockMode.PROBE)
}
val client = CoapClient(KtorUdpTransport.bind(), scope, clientConfig)
// Non-confirmable requests get Non-confirmable bursts;
// Confirmable ones go block by block.
val body = client.get("coap://192.0.2.1/big") { nonConfirmable() }.payload

The settings and calls of the guide’s Q-Block example, which GuideExamplesTest runs over real UDP in CI.

Security

Fail-closed message security

With OSCORE configured, nothing unprotected gets through by accident, in either direction.

  • Done: Server: every resource has an access policy, MessageSecurityRequired by default once security is set. A refused request gets 4.01, or 4.03 with an identity, before any handler, buffer, observation or burst.
  • Done: Client: it acts only on responses it verified. An unprotected error, which anyone on the path can send, is never repeated with its Echo or continued; the request fails with UNVERIFIED_RESPONSE.
  • Done: No silent plaintext: a request without a context fails instead of going out unprotected, unless allowUnprotected says otherwise.
  • Done: /.well-known/core lists only what the caller may use.

Server.kt

val server = CoapServer(
    KtorUdpTransport.bind("0.0.0.0", 5683),
    scope,
    CoapServerConfig(security = OscoreServer(contexts)),
) {
    resource("lights") {    // OSCORE only, by default
        get { CoapResponse.content("on for ${securityIdentity?.description}") }
    }
    resource("status") {
        access = AccessPolicy.Public  // for anyone, with or without OSCORE
        get { CoapResponse.content("up") }
    }
}

The README’s quick start, checked against the sources. ADR 0008 records the decision; AccessPolicyTest and UnverifiedResponseTest pin it.

Design

Sans-IO state machines

The protocol cores take bytes and the time, and return bytes and timers. Sockets and clocks live in thin adapters, so each layer is tested with fixed vectors on virtual time.

  • Done: CoAP messaging over datagrams and over streams, and the four Q-Block machines, run inside the endpoint.
  • Done: EDHOC’s EdhocInitiator and EdhocResponder are public API: message bytes in and out, transport left to you.
  • Done: OSCORE protects and verifies messages without the endpoint, so a proxy or another CoAP stack can use it.
  • Done: Time and randomness are injected; ephemeral keys too, which is how the RFC 9529 traces replay.
  • Open: A public sans-IO CoAP engine, for embedding in Netty or Vert.x event loops, is not built yet.

Platforms

One code base, every target

All protocol code is common Kotlin, with no expect/actual; the build fails a core module that grows code anywhere else.

  • Done: The same common tests run in CI on the JVM, Linux, macOS, the iOS simulator, and JS and Wasm on Node.js.
  • Done: Android uses the JVM artifacts from API level 26; CI checks the API level and builds a sample app with R8.
  • Done: Tests choose algorithms by what the backend supports, never by the platform they run on.
  • Open: Not yet run on an Android device or an iPhone. No linuxArm64, no Intel Apple targets.

Setup by platform

Cryptography

Capability-aware crypto

All cryptography goes through one asynchronous CryptoBackend. Protocol code asks what the backend supports, so a platform’s gaps become choices made up front, not failures halfway through a handshake.

  • Done: DefaultCryptoBackend runs on JCA, CryptoKit and CommonCrypto, OpenSSL 3 or WebCrypto. It probes each algorithm once and remembers the answer.
  • Done: supports(x) is false exactly when the operation would throw. EDHOC offers and accepts only the suites the backend runs.
  • Done: Small, public-data gaps get common-code fallbacks, such as AES-CCM on the AES block and point decompression. Secret-key algorithms do not.
  • Done: Private keys are opaque handles that protocol code never reads, so a hardware backend can hold them. None ships yet.

Open: Ed448 and suite 25; post-quantum beyond the JVM; a generated table of suites per platform. ADR 0001.

Build

A build that guards the API

The rules that keep kcoap portable and its API stable are checks in the build and in CI, not conventions.

ABI dumps

Every published module has committed JVM and klib API dumps. checkKotlinAbi fails on any change to them that is not committed with the code.

Common-only cores

verifyCommonOnly fails a core module that has main code outside commonMain.

Android API level 26

checkAndroidApi checks every jvm jar against the API 26 signature; checkAndroidApiDependencies checks the libraries behind them against a triaged baseline.

No hidden server engine

verifyNoServerEngine keeps a ktor server engine out of the WebSocket server’s published dependencies: the application chooses it.

Explicit API and opt-in markers

Explicit API mode everywhere. @ExperimentalKcoapApi marks what may change in any minor release, @InternalKcoapApi what is not API at all.

Coverage floor and DCO

koverVerify holds 90 % line coverage, 95 % for kcoap-edhoc. Every commit of a pull request needs a DCO sign-off.

Defaults

Security defaults

What kcoap does without being asked, and where it leaves a decision to you.

Amplification

Before a Q-Block burst or an Observe registration with Q-Block to an unverified address, the server checks the address with a 4.01 and Echo (RFC 9175). ALL_RESPONSES also covers every response more than three times its request.

Replay and freshness

OSCORE keeps a replay window of 32, and one per request for bodies of several responses. After a restart, the first request with old keys is challenged with Echo (Appendix B.1.2), unless the keys are new.

Sequence numbers

Pre-shared keys need a durable store, and kcoap has no default: you choose one. Every Partial IV is durable before its nonce is used.

Bounded state

Limits on deduplication entries, concurrent requests, exchanges and observers per peer, connections and bodies hold back unauthenticated peers; each is reported as an event when reached. The limits.

EDHOC sessions

A pending session answers only the peer that started it. At most 64 pending sessions, 8 per peer; they expire, and their secrets are wiped. Every authentication failure sends the same error.

Secrets and trust

Logs never contain EDHOC secrets, and secrets are copies wiped after use. No X.509 path validator ships yet: without one, only pinned credentials are trusted.

Found a vulnerability?

Do not open a public issue. Write to adrian.soltys@seelso.net with “kcoap security” in the subject; GitHub’s private reporting form will be the preferred channel once it is turned on for the repository. SECURITY.md has the details.

Testing

How kcoap is tested

Vectors first, then differential and fuzz tests, simulated networks on virtual time, stress tests on real threads, and live interop. CI runs on every pull request.

Differential tests

AES-CCM, AES-GCM, ChaCha20, SHAKE256, KMAC256 and SEC 1 points against Bouncy Castle; ECDSA encodings against the JDK.

Fuzzing

Seeded byte mutation on every target for the CBOR, CoAP, OSCORE, EDHOC, X.509 and DER parsers.

Lossy networks on virtual time

kcoap-testkit loses, duplicates and reorders datagrams, so a 93-second give-up is tested in milliseconds.

Stress on real threads

Concurrency tests on the thread pools of the JVM and Linux targets, and on the event loop of the web targets.

Same tests everywhere

The common tests run in CI on the JVM, Linux, macOS, the iOS simulator, and JS and Wasm on Node.js. Kover measures coverage on the JVM.
